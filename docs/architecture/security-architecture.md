# Архитектура безопасности

## 1. Аутентификация
- ASP.NET Core Identity, пароли — PBKDF2/Argon2-совместимый хэш Identity, политика: ≥10 символов; блокировка после 5 неудач (15 мин).
- JWT access 15 мин; refresh-токен 14 дней в httpOnly, Secure, SameSite=Lax cookie, ротация и отзыв при повторном использовании; хэш токена в БД.
- Для персонала — 2FA (TOTP) обязательна для Владельца (P1), опциональна для Администратора.
- Гость: email + пароль; вход по WhatsApp OTP — P2.

## 2. Авторизация (RBAC + Permissions)
Роль даёт набор разрешений; Владелец может добавлять/снимать разрешения у конкретного Администратора (`UserPermissions` с флагом grant/deny). Проверка — на backend через policy `[HasPermission("booking.cancel")]`. Объектные проверки (ownership): гость видит только свои сущности (`Booking.GuestUserId == currentUser`); уборщик — только свои задачи. Скрытие в UI — только удобство, не защита.

## 4. Защита API
- Валидация входа (FluentValidation), строгие DTO (без привязки сущностей), ограничения размеров.
- EF Core параметризованные запросы; сырой SQL только через параметры.
- XSS: React экранирует; CSP на Nginx/Next.js; санитайзинг любого пользовательского HTML (не допускается).
- CSRF: cookie SameSite=Lax + токен для небезопасных методов через BFF; API по Bearer не подвержен CSRF.
- Rate limiting: ASP.NET Core RateLimiter + Nginx `limit_req`: вход, регистрация, поиск доступности, публичные POST, вебхуки.
- CORS: только свой домен.
- Заголовки: HSTS, X-Content-Type-Options, Referrer-Policy, Frame-Options/CSP frame-ancestors.
- Загрузка файлов: белый список MIME, проверка сигнатур, переименование, хранение вне webroot, антивирус — P2.

## 5. Персональные данные
- Минимизация: документы только при законной необходимости, отдельное право.
- Шифрование чувствительных полей (номер документа) на уровне приложения (ключ вне БД, ротация); TLS везде; диск VPS зашифрован, если провайдер позволяет.
- Маскирование ПД в логах; доступ к ПД аудируется (кто и когда открыл документ).
- Сроки хранения и удаление/анонимизация по запросу — политика определяется после уточнения требований закона КР (см. вопросы).
- Согласия фиксируются в `GuestConsents`.

## 6. Секреты и конфигурация
Только переменные окружения/Docker secrets; `.env` в `.gitignore`; секрет-сканирование в CI; разные секреты для dev/prod; ключи банков и токен WhatsApp шифруются в БД или хранятся только в окружении.

## 7. Платёжная безопасность
Данные карт не принимаются и не хранятся (PCI scope минимален — перенаправление на страницу банка). Webhook: проверка подписи/секрета по документации банка, проверка суммы и валюты против нашего платежа, идемпотентность по `ProviderTransactionId`, запись сырого события в `WebhookEvents`. Подробно: `integrations/payment-integrations.md`.

## 8. Аудит
Логируются: вход/неудачи, смена ролей/прав, создание/изменение/отмена броней, платежи/возвраты, смена статусов номеров, доступ к документам, изменения настроек. Записи append-only, у приложения нет права UPDATE/DELETE на `AuditLogs`.

## 9. Резервное копирование и восстановление
Ежедневный `pg_dump` + WAL-архив (P1), хранение 14 дней локально и копия вне VPS, шифрование бэкапов, регулярная проверка восстановления (раз в месяц, чек-лист в README).

## 10. Угрозы и меры (кратко)
| Угроза | Мера |
|---|---|
| Двойное бронирование | exclusion constraint + транзакции |
| Повтор webhook/платежа | идемпотентность + unique-индексы |
| Подбор паролей | lockout + rate limit |
| Доступ к чужим броням (IDOR) | объектная авторизация + тесты |
| Утечка ПД | шифрование, минимизация, аудит |
| Подмена суммы онлайн | сверка суммы/валюты, расчёт только на backend |
| Злоупотребление публичными формами | rate limit, CAPTCHA (P1) |
