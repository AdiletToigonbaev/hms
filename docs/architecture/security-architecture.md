# Архитектура безопасности

## 1. Аутентификация
- ASP.NET Core Identity, хэш паролей Identity (PBKDF2). Политика: не менее 10 символов и не менее 4 разных символов; блокировка после 5 неудач на 15 минут. Для несуществующего логина выполняется проверка пароля-пустышки — время ответа не выдаёт наличие аккаунта; ответ одинаков (`auth.invalid_credentials`).
- JWT access 15 мин (HS256, ключ только из окружения, не короче 32 байт); refresh-токен 14 дней, в БД — только SHA-256 хэш, одноразовый (ротация), токены одной сессии образуют семейство; повтор заменённого токена позже 30 с — признак кражи, отзывается всё семейство. API принимает только Bearer; токены хранит сервер Next.js (BFF) в httpOnly, Secure (production), SameSite=Lax cookie — JavaScript браузера к ним доступа не имеет. Истёкший access-токен обновляет `proxy.ts` до рендера страницы.
- Access-токен на каждом запросе сверяется с актуальным состоянием пользователя (активен, SecurityStamp; кэш 30 с, сброс при изменении): блокировка, смена или сброс пароля действуют немедленно.
- Сотрудник создаётся с временным паролем и флагом `MustChangePassword`; до смены пароля API отвечает `403 auth.password_change_required` (кроме входа, профиля и смены пароля). Первый владелец создаётся командой `migrate` из переменных окружения `Bootstrap__Owner__*` — также с обязательной сменой пароля.
- Для персонала — 2FA (TOTP) обязательна для Владельца (P1), опциональна для Администратора.
- Гость: email + пароль; подтверждение email (настройка `RequireEmailConfirmation`); вход по WhatsApp OTP — P2; подтверждение регистрации кодом в WhatsApp — альтернатива письму (Sprint 10, работает после подключения WhatsApp).
- Ссылки подтверждения email и сброса пароля — одноразовые токены Identity с ограниченным сроком; ответы на «забыли пароль» не раскрывают, существует ли аккаунт.

## 2. Авторизация (RBAC + Permissions)
Роль даёт набор разрешений. **Права ролей «Администратор» и «Уборщик» настраивает владелец** (2026-11-22, экран «Сотрудники → Права ролей»; `role_permissions` с лимитом суммы); изменение сразу действует на всех сотрудников роли. Кроме того, владелец добавляет/снимает права конкретному администратору или уборщику (`UserPermissions` с флагом grant/deny и личным лимитом — он важнее лимита роли). Ограничения: владелец всегда имеет все права; права «только для владельца» не выдаются никому; уборщику доступны только `housekeeping.work` и `maintenance.create` (финансы и ПД гостей — инвариант). Свои роли (например, «Старший администратор») — в будущем, по решению заказчика. Проверка — на backend через policy `[HasPermission("booking.cancel")]`. Объектные проверки (ownership): гость видит только свои сущности (`Booking.GuestUserId == currentUser`); уборщик — только свои задачи. Скрытие в UI — только удобство, не защита.

## 4. Защита API
- Валидация входа (FluentValidation), строгие DTO (без привязки сущностей), ограничения размеров.
- EF Core параметризованные запросы; сырой SQL только через параметры.
- XSS: React экранирует; пользовательский HTML не допускается. CSP на Nginx (Sprint 11): `frame-ancestors 'none'; base-uri 'self'; object-src 'none'; form-action 'self'` — без `script-src`: строгий CSP требует nonce на каждый запрос, что несовместимо со статической оболочкой страниц Cache Components/PPR (обоснование — `development/deployment.md` §7).
- CSRF: все изменения из браузера выполняются через Server Actions Next.js — только POST, Next.js сверяет заголовок Origin с Host (запрос с чужого сайта отклоняется), cookie SameSite=Lax. API работает по Bearer и CSRF не подвержен.
- Rate limiting: ASP.NET Core RateLimiter по IP клиента (вход, регистрация, подтверждение и восстановление — 10/мин; обновление токенов — 60/мин; публичный подбор и расчёт цены — 60/мин). Создание и продление брони гостем — 10/мин **на аккаунт** (смена IP не помогает), плюс не больше 3 незаселённых броней с сайта на аккаунт — иначе один аккаунт мог бы удерживать весь номерной фонд неподтверждёнными бронями. Лимитер стоит после аутентификации, чтобы видеть пользователя. Nginx `limit_req` (Sprint 11) — только от флуда: страницы 100/с со всплеском 1000, вебхуки 10/с с IP (персонал выходит с одного IP, меню кабинета заранее подгружает разделы). Nginx **заменяет** `X-Forwarded-For` адресом клиента — подделать IP для лимитов API нельзя. IP клиента API получает из `X-Forwarded-For`, который передаёт BFF; доверие этому заголовку включается настройкой `ForwardedHeaders:TrustAllProxies` только там, где API не доступен из интернета напрямую.
- CORS: только свой домен.
- Заголовки (Nginx, Sprint 11): HSTS 1 год, X-Content-Type-Options, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy, CSP frame-ancestors. TLS 1.2/1.3; чужой Host и чужое имя TLS отклоняются. Снаружи к API — только `/api/v1/webhooks/`.
- Production-конфигурация: API и migrate не стартуют с ключами/паролями разработки или `PublicWebUrl` без https (`ProductionConfigurationCheck`).
- Загрузка файлов: белый список MIME, проверка сигнатур, переименование, хранение вне webroot, антивирус — P2.

## 5. Персональные данные
- Минимизация: документы только при законной необходимости, отдельное право.
- Шифрование чувствительных полей (номер документа) на уровне приложения (ключ вне БД, ротация); TLS везде; диск VPS зашифрован, если провайдер позволяет.
- Маскирование ПД в логах; доступ к ПД аудируется (кто и когда открыл документ).
- Сроки хранения и удаление/анонимизация по запросу — политика определяется после уточнения требований закона КР (см. вопросы).
- Согласия фиксируются в `GuestConsents`.

## 6. Секреты и конфигурация
Только переменные окружения/Docker secrets; `.env` в `.gitignore`; секрет-сканирование в CI; разные секреты для dev/prod; ключи банков и токен WhatsApp шифруются в БД или хранятся только в окружении.

## 7. Платёжная безопасность
Данные карт не принимаются и не хранятся (PCI scope минимален — перенаправление на страницу банка). Webhook: проверка подписи/секрета по документации банка, проверка суммы и валюты против нашего платежа, идемпотентность по `ProviderTransactionId`, запись сырого события в `WebhookEvents`. Подробно: `integrations/payment-integrations.md`.


### 7a. Сообщения и WhatsApp (Sprint 10)
- Вебхук `/api/v1/webhooks/whatsapp`: подпись `X-Hub-Signature-256` (HMAC-SHA256 сырого тела с App Secret, сравнение за постоянное время) до разбора JSON; без верной подписи — 401, событие не сохраняется; тело до 3 МБ; повтор отсекается по SHA-256 тела. Подтверждение адреса — Verify Token (сравнение за постоянное время). Без ключей на сервере вебхук отвечает 404.
- Секреты WhatsApp (токен, App Secret, Verify Token) — только в окружении; в БД — Phone Number ID и WABA ID.
- В outbox нет текста и контактов: только Id сообщения. Текст и адрес сообщений в БД стираются при обезличивании гостя; в логи не пишутся (только код шаблона и код ошибки).
- Код подтверждения регистрации: 6 цифр, хранится только SHA-256 (с Id пользователя), 10 минут, 5 попыток, новый — не чаще раза в минуту, эндпоинты под лимитом входа; после отправки код удаляется и из сообщения.
- Права: `whatsapp.send` — история, диалоги, ручная отправка (администратор по умолчанию); `whatsapp.templates.manage` — шаблоны, напоминания, автоответчик (только владелец). Уборщик сообщений не видит.
## 8. Аудит
Логируются: вход/неудачи, смена ролей/прав, создание/изменение/отмена броней, платежи/возвраты, смена статусов номеров, доступ к документам, изменения настроек. Записи append-only: триггер запрещает UPDATE/DELETE/TRUNCATE всем, а у роли приложения (Sprint 11) этих прав нет вовсе. API в production работает под ролью `hms_app` (`DatabaseAppRole`, создаёт команда migrate): только SELECT/INSERT/UPDATE/DELETE в схемах модулей, без DDL (не может отключить триггеры неизменяемости платежей и аудита), история миграций — только чтение. Миграции и бэкап — под владельцем схемы. Интеграционные тесты работают под такой же ролью.

## 9. Резервное копирование и восстановление
Реализовано в Sprint 11 (`development/deployment.md` §6): ежедневный `pg_dump` + загруженные файлы + манифест со сводкой → архив, зашифрованный **публичным** ключом age (приватный — у владельца вне сервера: доступ к VPS или хранилищу не раскрывает бэкапы); 14 дней на сервере, копия вне VPS через rclone (30 дней); healthcheck — нет успешного бэкапа 26 ч; проверка восстановления во временную БД со сверкой манифеста — раз в месяц (чек-лист); восстановление делает страховочный бэкап. WAL-архив (восстановление на любой момент) — P1, не настроен: потери — до суток.
