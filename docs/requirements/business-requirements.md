# Бизнес-требования HMS

## 1. Цель
Единая система управления гостиницей (10–30 номеров, Кыргызстан): бронирование, заселение/выселение, уборка, финансы, аналитика, публичный портал, WhatsApp-коммуникации.

## 2. Параметры
| Параметр | Значение |
|---|---|
| Валюта | KGS |
| Часовой пояс | Asia/Bishkek (UTC+6, без перехода на летнее время) |
| Язык | RU сейчас; KY, EN в перспективе (i18n с первого дня) |
| Объект | 1 гостиница; модель данных готова к нескольким (`HotelId` во всех бизнес-таблицах) |
| Устройства | ПК, планшет, смартфон (responsive; интерфейс уборщика mobile-first) |

## 3. Решения заказчика (зафиксированы)
1. **Онлайн-эквайринг (MBANK, Optima) подключается обязательно, но после готовности веб-приложения.** Архитектура готовится сейчас, реализация адаптеров — после получения документации и доступов.
2. **WhatsApp Business**: номер и доступы будут предоставлены заказчиком позже. Интеграция разрабатывается через адаптер и проверяется после получения доступов.
3. Структуру БД архитектор вправе менять по необходимости.
5. **Почасовые брони (2026-11-20).** Основной поток гостиницы — брони на часы; посуточные брони тоже остаются. Цена почасовой брони = цена часа категории (или номера, или тарифа) × часы, минимум N часов (по умолчанию 2). После почасовой брони номер закрыт на уборку на 30 минут (настройка). Гость сможет бронировать часы на сайте так же, как администратор. Время начала — с шагом 1 час.
7. **Правила почасовых броней (2026-11-21):** неявка — через 30 мин после начала (номер освобождается); неподтверждённая бронь держит номер 30 мин, но не позже начала; досрочный выезд — оплата фактических часов. Все значения — настройки владельца; подробно — `development/development-roadmap.md` §6.1a.
9. **Номер брони со смыслом (2026-11-21):** «Ч-2111-07» — Ч (почасовая) / С (посуточная), день создания, номер за день. Номер не меняется при переносе, не выдаёт общее число броней, легко диктуется. Старые брони сохраняют прежние номера.
8. **Штрафов по умолчанию нет (2026-11-21).** У заказчика нет системы штрафов: все штрафы (поздняя отмена, неявка, досрочный выезд; почасово и посуточно) по умолчанию равны нулю — отмена бесплатна в любое время, неявка без штрафа. Механизм штрафов сохранён: владелец включает и настраивает их сам после установки («Настройки → Правила брони»). Сроки бесплатной отмены (24 ч / 2 ч) остаются в настройках и начинают действовать, только когда задан штраф.
10. **Детских тарифов нет (2026-11-22).** Отдельной цены за ребёнка нет и не планируется: дети учитываются только во вместимости номера (взрослые + дети ≤ вместимость). Пункт убран из плана (P1).
11. **Права ролей и сотрудников (2026-11-22).** Владелец настраивает права ролей «Администратор» и «Уборщик» (с лимитами сумм) и личные права каждого сотрудника. Свои роли (например, «Старший администратор») пока не нужны — добавить в будущем.
12. **Гость выбирает конкретный номер на сайте (2026-11-23).** После поиска сайт показывает свободные номера, сгруппированные по категориям: фото номера (нет своих — фото категории), номер комнаты, этаж, кровати, цена. Номер комнаты гость видит до брони и в кабинете. Если выбранный номер успели занять — бронь не создаётся (409), другой номер система сама не подставляет. Заменяет решение Sprint 8 «гость выбирает категорию, номер подбирает система».
6. **Продление брони (2026-11-20).** Если гость хочет остаться дольше, администратор продлевает бронь: почасовую — на N часов, посуточную — на N ночей. Продление возможно, только если номер свободен на добавленное время (с учётом уборки); иначе — отказ с понятной ошибкой. Добавленное время оплачивается по ценам на момент продления, исходная стоимость брони не пересчитывается. Каждое продление пишется в историю брони и аудит.
4. Противоречия в документах этапа 1 архитектор устраняет на своё усмотрение (решение заказчика от 2026-11-20). Принятые решения отражены в документах; бизнес-параметры, требующие подтверждения, вынесены в настройки и перечислены в `development/development-roadmap.md` §6.

## 3a. Отклонения от ТЗ (осознанные)
| Требование ТЗ | Решение | Основание |
|---|---|---|
| §2, §3.4: онлайн-оплата MBANK/Optima обязательна | Реализуется после готовности веб-приложения (P2); до этого — ручная регистрация платежей. Домен платежей, статусы и `IPaymentProvider` создаются сразу | Решение заказчика (§3 п.1); ТЗ §10: «если доступ к API или документации отсутствует, подготовить архитектуру адаптера» |
| §3.4: подтверждения через WhatsApp | Домен, шаблоны, outbox — в MVP; реальная отправка — после выдачи доступов | Решение заказчика (§3 п.2) |
| §3, §4: дата заезда/выезда, «стоимость за ночь» | Два вида брони: **посуточная** (как в ТЗ) и **почасовая** (дата, время начала, число часов; цена за час). Защита от пересечений — по времени: посуточная бронь занимает номер с часа заезда до часа выезда, почасовая — с начала до конца плюс время на уборку | Решение заказчика (§3 п.5) |
| §20: «после подтверждения начинай Sprint 1» | Перед Sprint 1 выполняется Sprint 0 (каркас, CI) | Указание заказчика; Sprint 0 не содержит бизнес-логики |

Все остальные требования ТЗ входят в MVP (P0), кроме явно помеченных в ТЗ как необязательные («при необходимости»: фотоотчёт уборки, дата рождения).

## 4. Режимы оплаты по фазам
| Фаза | Оплата | Поведение бронирования с сайта |
|---|---|---|
| MVP (до эквайринга) | Только ручная регистрация платежей администратором | Бронь создаётся как `Pending` со сроком `ConfirmDueAt` (настройка `PendingHoldHours`, по умолчанию 24 ч); администратор подтверждает (или авто-подтверждение по настройке `AutoConfirmWebBookings`) → `Confirmed`; не подтверждённая в срок → `Expired`. Оплата при заезде/переводом |
| После подключения банков | Онлайн-оплата MBANK/Optima | `AwaitingPayment` с таймером → `Confirmed` по подтверждённому webhook |

Переключение — флаг `OnlinePaymentEnabled` в настройках. Статусы и таблицы платежей существуют с первого дня.

## 5. Бизнес-цели и метрики
- Исключить двойные бронирования (0 допустимых конфликтов).
- Прозрачный учёт: начисления ≠ полученные платежи ≠ возвраты ≠ расходы.
- Владелец видит Revenue, Net Revenue, Expenses, Net Profit, Occupancy, ADR, RevPAR, отмены, задолженности по фактическим данным.
- Сокращение ручных сообщений гостям за счёт WhatsApp-автоматизации.

## 6. Роли
Владелец, Администратор, Уборщик, Гость. Матрица прав: `architecture/security-architecture.md`.

## 7. Допущения
- Один часовой пояс; даты проживания хранятся как `date` в локальной зоне отеля.
- Цена за ночь по категории/номеру с возможностью сезонных тарифов и цен выходных (владелец).
- Дополнительные услуги — справочник с ценой (завтрак, доп. место, ранний заезд, поздний выезд — тоже услуги).
- Цены вводятся конечными; налоги не рассчитываются (решение заказчика 2026-11-20).
- Фискализация (ККТ, чеки) не нужна: система чеки не выдаёт и не учитывает (решение заказчика 2026-11-20).
- Значения бизнес-правил по умолчанию (время заезда/выезда, отмена, No-Show, удержание брони) — настраиваемые; см. `development/development-roadmap.md` §6.
- Данные карт не хранятся и не обрабатываются системой (оплата на стороне банка).

## 8. Юридические и регуляторные вопросы (решения заказчика 2026-11-20)
- Фискализация и налоги — не требуются (см. §7).
- Паспортные и иные данные документов гостей не хранятся; регистрация иностранных граждан ведётся вне системы.
- Данные гостя хранятся, пока владелец не удалит (обезличит) карточку; удаление — вручную.
- Согласие на WhatsApp-рассылки — по-прежнему фиксируется (`GuestConsents`). Подробности — `development/development-roadmap.md` §6.2.

## 9. Вне объёма первой версии
Мультиотельность в UI, channel manager (Booking.com и др.), IoT/замки, интеграция с 1С, нативные мобильные приложения, динамическое ценообразование, детские тарифы (решение заказчика 2026-11-22).
