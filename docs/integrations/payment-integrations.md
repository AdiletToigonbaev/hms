# Интеграции онлайн-оплаты: MBANK и Optima Bank

## 1. Статус
**Решение заказчика:** подключение обязательно, но после готовности веб-приложения. Заявку на эквайринг подаёт заказчик.
**Что мы НЕ знаем и не придумываем:** URL, формат запросов, схему подписи, список статусов, поддержку возвратов/холдов, комиссии, тестовые реквизиты MBANK и Optima. Всё это определяется только официальной документацией банка, выдаваемой при подключении.

## 2. Что сделать сейчас (без документации)
1. Домен `Payments` целиком (Payments, PaymentTransactions, Refunds, статусы, идемпотентность, ручные способы).
2. Интерфейс провайдера:
```csharp
interface IPaymentProvider {
  string Code { get; }                                   // "mbank" | "optima"
  Task<CreatePaymentResult> CreatePaymentAsync(CreatePaymentRequest r, CancellationToken ct);
  Task<ProviderPaymentStatus> GetStatusAsync(string externalId, CancellationToken ct);
  Task<RefundResult> RefundAsync(RefundRequest r, CancellationToken ct);
  WebhookVerification VerifyWebhook(HttpRequestData req);  // подпись по документации банка
  WebhookEvent ParseWebhook(HttpRequestData req);
}
```
3. Единый конвейер вебхука: сырой запрос → `WebhookEvents` (unique Source+DedupKey) → проверка подлинности → поиск платежа → проверка суммы/валюты → переход статуса в транзакции → ответ банку.
4. Флаг `OnlinePaymentEnabled`=false; в UI онлайн-оплата скрыта; бронь работает через `Pending → Confirmed` администратором.
5. Фоновая сверка: платежи в `Processing` старше N минут запрашиваются у банка `GetStatus`.
6. **Заглушки-имитаторы успешной оплаты не создаются** (требование ТЗ). Для тестов используются только fake-провайдер в unit-тестах (в тестовом проекте, недоступный в production-сборке) и sandbox банка после получения.

## 3. Жизненный цикл платежа
`Pending` (создан у нас) → `Processing` (ссылка выдана/гость на стороне банка) → `Paid` | `Failed` | `Cancelled`. Возвраты: `Paid → RefundPending → Refunded | PartiallyRefunded`.
Бронь `AwaitingPayment → Confirmed` только после `Paid`, подтверждённого проверенным webhook или проверенным запросом статуса к банку (не по редиректу браузера).

## 4. Требования безопасности и надёжности
- Подлинность вебхука: способ определяется документацией (подпись/секрет/IP-allowlist); без валидной проверки — не обрабатывать, 401/403 и запись в `WebhookEvents` с `SignatureValid=false`.
- Идемпотентность: по `ProviderTxnId`/event id; повторный webhook → 200 без побочных эффектов.
- Сверка суммы и валюты (KGS) с нашей записью; расхождение → `payment.amount_mismatch`, платёж в ручную проверку.
- Параллельные вебхуки/редирект: блокировка строки платежа (`FOR UPDATE`).
- Карточные данные не принимаются, не логируются. Сырой ответ логируется после удаления чувствительных полей.
- Секреты банка — только окружение/секрет-хранилище; раздельно sandbox/prod.
- Таймауты и ретраи с backoff на исходящие вызовы; circuit breaker.
- Возврат: ограничение суммой оплаты за вычетом прошлых возвратов; утверждение по правам.
- Страница возврата гостя после оплаты показывает статус, полученный от нашего backend, а не параметры URL.

## 6. План подключения после получения документации
1. Анализ документации; уточнения у банка; обновить этот документ.
2. Реализация `MbankPaymentProvider` / `OptimaPaymentProvider` + конфигурация.
3. Контрактные тесты по примерам из документации; тесты вебхуков (подпись, повтор, неверная сумма, гонка).
4. Тестирование в sandbox по чек-листу банка (успех, отказ, отмена, таймаут, возврат).
5. Сертификация/приёмка банком, боевые ключи, включение флага.
6. Мониторинг: метрики платежей, алерты на `Processing` > N минут и непроверенные вебхуки.

## 7. Открытые вопросы
Поддерживают ли банки двухстадийные платежи (hold), частичные возвраты, повторные ссылки, отмену до расчёта; формат webhook (JSON/форма); нужна ли отдельная фискализация; можно ли использовать оба банка параллельно на одном мерчанте; срок жизни платёжной ссылки.
